# 第 10 课（第三部分）：公共子表达式与重复计算消除

前两部分分别看到优化器可以让函数调用边界消失，也可以把 `call + ret` 改写为尾跳转。本节继续处理另一类常见变化：**源码里看起来重复出现的计算，不一定会在最终机器代码里重复执行。**

这类变化是阅读优化汇编时最容易造成误判的来源之一。源码可能定义多个中间变量，但最终寄存器中只保留一个机器级值；源码可能写了两次同样的表达式，但反汇编里只出现一次真正的加法和乘法。

## 1. 问题背景：源码变量不是机器状态的一一映射

考虑：

```c
long x = (a + b) * c;
long y = (a + b) * c;
return x + y;
```

如果完全按照源码逐句机械翻译，可以想象成：

```text
计算 a+b
乘以 c
保存为 x
再次计算 a+b
再次乘以 c
保存为 y
最后计算 x+y
```

这在语义上当然正确，但不是唯一正确实现。

因为：

```text
x == y == (a + b) * c
```

只要中间没有改变相关值，也没有必须保留的可观察副作用，机器代码完全可以只计算一次共同结果，然后复用它。

因此阅读优化汇编时要先建立一个重要模型：

```text
源码变量
    是语言层面的名称

机器寄存器 / 栈槽
    是某个时刻保存机器级 value 的位置
```

两者不是固定一一对应关系。

## 2. 什么是公共子表达式

如果两个表达式在某个有效范围内计算同一个值，例如：

```text
(a + b) * c
```

第一次已经算出结果，而在第二次使用前：

- `a` 没有改变；
- `b` 没有改变；
- `c` 没有改变；
- 计算本身没有必须重复发生的可观察副作用；

那么第二次重新执行相同计算通常是冗余的。

优化器可以复用第一次得到的值。这种现象通常会与 common subexpression elimination、value numbering、表达式规范化、代数化简等优化技术相关。

这里要特别避免过度归因：**从最终反汇编只能可靠确认“重复计算消失了”，不能仅凭几条机器指令断言一定由 GCC 某一个固定 pass 独立完成。**

## 3. 本实验的控制方法

实验固定源码：

```c
__attribute__((noinline)) long repeated_expr(long a, long b, long c)
{
    long x = (a + b) * c;
    long y = (a + b) * c;
    return x + y;
}
```

并构建：

```text
-O0
-Og
-O2
```

`noinline` 只用于保证 `repeated_expr()` 本身保留为独立函数，方便稳定反汇编；它不强制函数体内部关闭公共表达式相关优化。

参数按照 SysV AMD64 ABI 进入函数：

```text
a -> %rdi
b -> %rsi
c -> %rdx
```

整数返回值通过 `%rax` 返回。

## 4. `-O0`：源码中的两次计算基本按原结构保留

本次 GCC 14.2.0 的 `-O0` 反汇编中，参数先被写入栈槽，随后第一次表达式执行：

```asm
mov    -0x18(%rbp),%rdx
mov    -0x20(%rbp),%rax
add    %rax,%rdx
mov    -0x28(%rbp),%rax
imul   %rdx,%rax
mov    %rax,-0x8(%rbp)
```

之后第二次表达式又重新加载参数并执行第二组：

```asm
mov    -0x18(%rbp),%rdx
mov    -0x20(%rbp),%rax
add    %rax,%rdx
mov    -0x28(%rbp),%rax
imul   %rdx,%rax
mov    %rax,-0x10(%rbp)
```

最后再把两个栈槽相加。

这个版本很适合作为基线，因为它使源码变量、栈槽和重复计算之间的关系比较直观。

但即使是 `-O0`，也不应把具体偏移当成 ABI 规则。`-0x8(%rbp)`、`-0x10(%rbp)` 只是本次 GCC 的代码生成结果。

## 5. `-Og/-O2`：公共结果只真实计算一次

同一函数在本次 `-Og` 和 `-O2` 下都变为：

```asm
add    %rsi,%rdi
imul   %rdx,%rdi
lea    (%rdi,%rdi,1),%rax
ret
```

逐条跟踪机器状态：

### 5.1 `add %rsi,%rdi`

进入函数时：

```text
RDI = a
RSI = b
RDX = c
```

执行后：

```text
RDI = a + b
```

`RSI` 和 `RDX` 不变。

### 5.2 `imul %rdx,%rdi`

AT&T 两操作数形式中，目标操作数是第二个操作数，因此：

```text
RDI = RDI * RDX
    = (a + b) * c
```

现在 `%rdi` 中已经保存两个源码表达式共同的值。

### 5.3 `lea (%rdi,%rdi,1),%rax`

这里：

```text
RAX = RDI + RDI
    = 2 * ((a + b) * c)
    = x + y
```

于是最终只执行了一次 `a+b` 和一次乘法。

源码中仍然有 `x`、`y` 两个名称，但机器代码不需要让它们分别占用两个寄存器或两个栈槽。

## 6. 这里的寄存器生命周期应该怎样理解

优化后的代码中，可以把 `%rdi` 的 value 生命周期分成两个阶段：

```text
函数入口
RDI = a

add 后
RDI = a + b

imul 后
RDI = (a + b) * c

lea 读取 RDI
RAX = 2 * RDI
```

同一个物理寄存器在不同时间保存不同语义的 value。

这正是后面学习寄存器分配时必须掌握的基础：

> 不能说“RDI 就是变量 a”。更准确的说法是，在函数入口处 `%rdi` 根据 ABI 携带参数 `a`；之后编译器可以复用 `%rdi` 保存新的中间值。

ABI 只约束函数调用边界上的参数/返回规则，并不要求 callee 在整个函数执行期间保持参数寄存器的初始内容。

## 7. `RFLAGS` 在这个例子中的变化

本节虽然重点是数据依赖，但仍需检查标志位：

```asm
add    %rsi,%rdi
```

会根据加法结果更新 `CF/ZF/SF/OF` 等算术标志位。

```asm
imul   %rdx,%rdi
```

两操作数有符号乘法会根据结果是否能在目标宽度中正确符号扩展来设置 `CF/OF`；其他算术标志位不应作为后续程序逻辑的可靠输入。

```asm
lea    (%rdi,%rdi,1),%rax
```

不会更新 `RFLAGS`。

本函数没有条件跳转，也没有在返回值中读取这些 flags，因此优化器不需要保留某个源码算术操作之后的标志位状态。

这也是为什么不能只比较“源码算了几次”判断机器状态是否相同；如果 flags 的可观察语义不同，合法优化的空间也会不同。

## 8. 为什么有些看起来相同的表达式不能直接合并

公共值复用需要满足语义条件。下面情况不能简单套用本实验结论。

### 8.1 输入值在中间被修改

```c
x = a + b;
a++;
y = a + b;
```

第二次表达式的输入已经不同。

### 8.2 存在可能改变内存值的操作

如果表达式依赖某个内存位置，而中间存在可能修改该位置的函数调用、别名写入或其他 store，编译器必须证明旧值仍然有效才能复用。

### 8.3 `volatile` 访问

对 `volatile` 对象的访问本身具有语言层面的可观察约束，不能把它当成普通无副作用值随意删除或合并。

### 8.4 可能影响程序语义的异常或边界

整数溢出语义、浮点环境、trap 行为以及语言规则都会影响某些变换是否合法。不能把纯数学等价直接等同于 C 语言语义等价。

## 9. 公共表达式消除和寄存器分配不是同一件事

本实验中最终只需要一个 `%rdi` 保存共同中间值，看起来好像“公共表达式优化就是寄存器优化”。这两个概念应分开：

```text
公共值识别/冗余计算消除
    决定哪些计算不必重复执行

寄存器分配
    决定仍然活跃的机器级 value 放在哪个物理寄存器或是否 spill
```

二者会相互影响，但不是同一个问题。
