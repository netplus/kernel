# 第 5 课：循环、状态机与 `switch`

前面的课程已经介绍了比较、条件跳转、基本块和整数运算。本课把这些基础组合起来，分析 C 语言中的循环、状态机和 `switch` 最终怎样变成机器控制流。

本课先建立一个基本认识：

```text
while、for、switch、状态机
```

这些都是源代码层面的结构。CPU 并不直接执行“循环”或“switch”，CPU 实际执行的是：

```text
比较或测试
→ 修改标志位
→ 条件跳转或间接跳转
→ 执行一个基本块
→ 再决定下一条路径
```

因此，阅读优化后的汇编时，不要强求汇编仍然保持 C 源代码的外形。更可靠的方法是先恢复基本块和基本块之间的跳转关系。

---

## 1. 先建立控制流图的概念

一个基本块可以简单理解为：

> 从入口开始顺序执行，中间没有其他跳转入口，直到最后一条控制转移指令为止的一段代码。

例如：

```asm
.Ltest:
    cmpq $5, %rcx
    jg .Ldone

.Lbody:
    addq %rcx, %rax
    incq %rcx
    jmp .Ltest

.Ldone:
```

可以画成：

```text
        ┌─────────┐
        │  test   │
        └────┬────┘
         <=5 │  >5
             │
      ┌──────▼──────┐
      │    body     │
      └──────┬──────┘
             │
             └──────────→ test

                    >5 → done
```

其中从 `body` 返回 `test` 的边称为回边。循环之所以形成，本质上就是控制流图中存在一条回到前面基本块的路径。

后面阅读循环时，重点观察四个位置：

```text
初始化
条件检查
循环体
状态更新和回边
```

---

## 2. `while` 循环

考虑：

```c
long sum = 0;
long i = 1;

while (i <= 5) {
    sum += i;
    i++;
}
```

一种直接的汇编形式是：

```asm
    xorq %rax, %rax      # sum = 0
    movq $1, %rcx        # i = 1

.Ltest:
    cmpq $5, %rcx
    jg .Ldone

    addq %rcx, %rax
    incq %rcx
    jmp .Ltest

.Ldone:
```

这里的控制过程很清楚：

```text
先检查条件
→ 条件成立时执行循环体
→ 更新 i
→ 跳回条件检查
```

这与 `while` 的语义一致，因为 `while` 在第一次执行循环体之前就要检查条件。

### 2.1 为什么有两个跳转

上面的代码包含：

```asm
jg  .Ldone
jmp .Ltest
```

它们承担不同作用：

- `jg` 根据条件决定是否退出循环；
- `jmp` 无条件形成回边，使控制流重新回到循环头。

编译器也可能重新排列基本块，让常见路径通过顺序执行完成，从而减少某个无条件跳转。因此不能只根据“有没有 `jmp`”判断是否存在循环。

真正需要寻找的是：

> 控制流是否能够回到之前已经执行过的基本块。

---

## 3. `do-while` 循环

考虑：

```c
do {
    sum += n;
    n--;
} while (n != 0);
```

它的直接汇编形式可能是：

```asm
.Lbody:
    addq %rcx, %rax
    decq %rcx
    jne .Lbody
```

与 `while` 最大的区别是：

```text
while       先检查条件，再执行循环体
do-while    先执行循环体，再检查条件
```

因此，`do-while` 在结构上经常更加紧凑：循环体末尾的一次条件跳转就可以同时完成条件检查和回边。

例如：

```asm
decq %rcx
jne .Lbody
```

`decq` 更新 `ZF`，`jne` 随后读取 `ZF`。当 `%rcx` 减到 0 时，`ZF=1`，循环结束。

这里也再次体现了第 3 课中的规律：

```text
产生标志位的指令
→ 消费标志位的条件指令
```

---

## 4. `for` 循环并没有特殊机器指令

C 代码：

```c
for (i = 0; i < nr; i++)
    sum += array[i];
```

逻辑上可以展开成：

```c
i = 0;
while (i < nr) {
    sum += array[i];
    i++;
}
```

因此，x86 并不需要一条专门对应 C `for` 的指令。

编译器只需要生成：

```text
初始化
→ 条件检查
→ 循环体
→ 更新
→ 回边
```

### 4.1 数组索引遍历

一种形式是：

```asm
movq (%rdi,%rcx,8), %rdx
addq %rdx, %rax
incq %rcx
```

其中 `%rcx` 是数组索引。

### 4.2 指针遍历

编译器也可能不用显式索引，而直接移动指针：

```asm
addq (%rsi), %rax
addq $8, %rsi
```

如果已知数组结束地址，还可以比较两个指针：

```text
current pointer == end pointer ?
```

因此，看到一个 C 数组循环时，汇编中不一定存在明显的 `i`。

编译器关注的是地址如何变化，而不是保留源代码变量的形式。

## 5. `break` 和 `continue`

这两个语句也只是控制流变化。

### `break`

```c
if (value == 0)
    break;
```

通常意味着直接跳向循环出口：

```asm
testq %rax, %rax
je .Lloop_exit
```

### `continue`

```c
if (skip)
    continue;
```

通常意味着跳向：

```text
for 循环的更新部分
```

或者：

```text
while 循环的下一次条件检查
```

因此分析复杂循环时，不要假设只有一条回边，也不要假设只有一个循环出口。

## 6. 状态机：循环加状态变量

很多系统代码不会表现为简单的“计数到 N”，而是根据当前状态选择不同处理逻辑。

例如：

```text
INIT
→ READY
→ RUNNING
→ DONE
```

可以写成：

```c
for (;;) {
    switch (state) {
    case INIT:
        prepare();
        state = READY;
        break;

    case READY:
        start();
        state = RUNNING;
        break;

    case RUNNING:
        finish();
        state = DONE;
        break;

    case DONE:
        return;
    }
}
```

机器层面可以理解成：

```text
状态分发块
→ 状态 0 处理块
→ 更新 state
→ 回到状态分发块

状态分发块
→ 状态 1 处理块
→ 更新 state
→ 回到状态分发块

...
```

所以状态机本质上仍然由几个基本元素组成：

```text
状态变量
分支选择
状态处理块
状态更新
回边
```

### 6.1 阅读状态机时先记录状态变化

看到较复杂的汇编时，可以先建立表格：

| 当前状态 | 条件 | 动作 | 下一状态 |
|---|---|---|---|
| INIT | 初始化成功 | 准备资源 | READY |
| READY | 可以运行 | 开始工作 | RUNNING |
| RUNNING | 工作完成 | 收尾 | DONE |

这种方法比一开始追踪所有指令更容易恢复程序逻辑。

### 6.2 优化后状态变量可能消失

如果状态变化完全可以在编译期推导，编译器可能把多个状态直接合并。

例如：

```text
INIT 一定进入 READY
READY 一定进入 RUNNING
RUNNING 一定进入 DONE
```

如果中间没有外部可观察事件，优化器可能直接计算最终结果。

所以：

> 源代码中存在状态机，不代表优化后的汇编仍然存在一个明确的 `state` 变量。

## 7. `switch` 的基本问题

考虑：

```c
switch (op) {
case 0:
    ...
    break;
case 1:
    ...
    break;
case 2:
    ...
    break;
default:
    ...
}
```

CPU 需要解决的问题只有一个：

> 根据 `op` 的值，选择应该进入哪个基本块。

编译器有多种实现方法。

常见方法包括：

```text
逐项比较
树形比较
条件移动
数据查找表
跳转表
```

选择哪一种取决于：

- `case` 数量；
- 数值是否连续；
- 数值范围是否很大；
- 每个分支做什么；
- 优化级别；
- 编译器版本和目标架构。

因此不能看到 `switch` 就直接断定一定存在跳转表。

---

## 8. 稀疏 `switch`：比较通常更合适

例如：

```c
switch (op) {
case 1:
    ...
case 10:
    ...
case 100:
    ...
case 1000:
    ...
}
```

如果建立一个覆盖 `0..1000` 的跳转表，其中绝大部分位置都只能指向 `default`，会浪费较多空间。

编译器更可能使用：

```asm
cmpl $100, %edi
je   .Lcase100
ja   .Llarge

cmpl $1, %edi
je   .Lcase1

cmpl $10, %edi
je   .Lcase10
```

这不一定是从小到大逐项比较。编译器可以调整比较顺序，把它组织成类似决策树的结构。

---

## 9. 稠密 `switch`：跳转表

考虑连续的：

```text
case 0
case 1
case 2
case 3
case 4
case 5
```

一种常见实现是跳转表。

实验中的核心代码为：

```asm
    leaq .Lswitch_table(%rip), %rdx
    cmpq $5, %rdi
    ja .Ldefault

    movslq (%rdx,%rdi,4), %rax
    addq %rdx, %rax
    jmp *%rax
```

跳转表保存每个 case 相对于表基址的偏移：

```asm
.Lswitch_table:
    .long .Lcase0 - .Lswitch_table
    .long .Lcase1 - .Lswitch_table
    .long .Lcase2 - .Lswitch_table
    .long .Lcase3 - .Lswitch_table
    .long .Lcase4 - .Lswitch_table
    .long .Lcase5 - .Lswitch_table
```

下面逐步分析。

### 9.1 先做范围检查

```asm
cmpq $5, %rdi
ja .Ldefault
```

这里把 `%rdi` 当作无符号值检查是否大于 5。

如果超出范围，就不能直接用它索引跳转表，否则可能从表外读取错误地址。

### 9.2 计算表项位置

```asm
movslq (%rdx,%rdi,4), %rax
```

地址为：

```text
table_base + op * 4
```

每个表项为一个 32 位相对偏移，所以比例因子是 4。

`movslq` 把这个 32 位有符号偏移扩展为 64 位。

### 9.3 得到目标地址

```asm
addq %rdx, %rax
```

得到：

```text
target = table_base + relative_offset
```

### 9.4 间接跳转

```asm
jmp *%rax
```

这和：

```asm
jmp .Lcase4
```

不同。

直接跳转的目标编码在指令中，而间接跳转的目标在运行时由寄存器给出。

因此，跳转表实现的核心是：

```text
case 值
→ 表索引
→ 目标地址
→ 间接跳转
```

---

## 10. 为什么使用相对偏移而不是绝对地址

跳转表可以保存绝对目标地址，也可以保存相对于某个基址的偏移。

现代编译器在位置无关代码中经常使用相对偏移，例如：

```text
case_target - table_base
```

这样表内容不必保存完整 64 位运行地址，也更容易配合位置无关代码。

这与第 2 课中的 RIP-relative 寻址可以联系起来理解：

> 程序尽量根据“当前位置或某个已知基址 + 偏移”找到目标，而不是把固定虚拟地址写死在代码里。

## 11. `switch` 还可能变成数据查找表

如果每个 `case` 只是返回一个常量：

```c
switch (op) {
case 0: return 11;
case 1: return 37;
case 2: return 4;
...
}
```

编译器可能发现根本不需要跳转到六段代码。

它可以直接建立：

```text
11, 37, 4, 82, 19, 55
```

这样的数据表，然后根据 `op` 读取结果。

这时会看到“表索引”，却可能看不到间接 `jmp`。

因此分析优化代码时要先区分：

```text
这是目标地址表？
还是普通结果数据表？
```

## 12. 编译器会重新组织循环

简单循环在 `-O2` 下可能出现：

```text
循环展开
强度削弱
指针化遍历
提前计算
条件合并
分支反转
```

例如：

```c
for (i = 0; i < 4; i++)
    sum += array[i];
```

如果数组内容和循环次数在编译期完全已知，循环甚至可能完全消失。

所以阅读编译器输出时，建议按以下顺序：

```text
1. 找函数入口和出口
2. 找所有条件跳转和间接跳转
3. 标记跳转目标
4. 划分基本块
5. 寻找回边
6. 判断哪些块构成循环
7. 再恢复变量和高级语言语义
```

不要反过来要求每条汇编必须对应某一行 C。

## 13. x86 的 `loop` 指令

x86 本身存在：

```asm
loop target
```

它会修改计数寄存器并根据结果决定是否跳转。

但是在现代编译器生成的普通循环中，更常见的是：

```asm
dec / inc / add
cmp / test
jcc
```

原因包括代码生成灵活性和现代处理器上的执行特性。

因此，学习 C 循环的汇编实现时，不应把“循环”与 `loop` 这条具体指令绑定起来。

## 14. 与 Linux 内核代码的关系

内核源码中大量存在：

```text
链表或数组遍历
重试循环
等待条件变化的循环
状态机
错误处理中的多出口控制流
switch 分发
```

阅读这些代码的反汇编时，可以沿用本课的方法。

### 遍历代码

先找：

```text
当前指针
下一对象地址
终止条件
回边
```

### 重试循环

先找：

```text
尝试操作
失败条件
状态更新
是否回到重试点
```

### 状态机

先记录：

```text
当前状态
进入哪个处理块
处理后状态如何变化
是否回到分发位置
```

### `switch`

先判断：

```text
比较链？
跳转表？
结果查找表？
```

这些方法比仅仅搜索函数名更适合阅读优化后的内核反汇编。

## 15. 常见误区

### 误区一：看到后向 `jmp` 就一定是源代码循环

后向跳转通常提示存在回边，但编译器生成的控制流、错误重试和手写汇编也可能产生类似结构。仍要结合整个 CFG 判断。

### 误区二：`for` 一定有明确的循环变量

优化后可能只剩一个移动的指针和结束地址。

### 误区三：`switch` 一定使用跳转表

稀疏 case 往往更适合比较；非常简单的 case 甚至可能变成数据查表。

### 误区四：跳转表中保存的一定是完整地址

常见实现保存的是 32 位相对偏移，需要和表基址相加才能得到目标地址。

### 误区五：状态机中的每个状态一定对应独立基本块

优化器可能合并状态、提前计算，甚至删除整个中间状态。

## 16. 本课应形成的分析方法

面对一段包含循环或多分支的反汇编，按下面的顺序分析：

```text
第一步：找所有控制转移指令
第二步：标记所有跳转目标
第三步：划分基本块
第四步：画出基本块之间的边
第五步：寻找回边，确定循环范围
第六步：判断比较使用 signed 还是 unsigned 语义
第七步：恢复循环变量、指针或状态变量
第八步：判断 switch 使用比较还是表驱动
```

完成这些步骤后，再对应回 C 源代码会容易很多。
