# 第 4 课：整数算术、位运算、移位、乘法与除法

前三课解决了三个基础问题：数据放在哪里、地址如何计算、CPU 如何根据运算结果改变控制流。本课继续研究 CPU 怎样完成整数计算。

这一课的重点不是记住更多指令名称，而是建立下面几个判断习惯：

```text
操作数是多少位？
当前只关心低位结果，还是需要完整结果？
数据按有符号还是无符号解释？
这条指令会修改哪些标志位？
是否存在隐式使用的寄存器？
```

这些问题在阅读编译器输出和 Linux 内核反汇编时会反复出现。

---

## 1. 整数运算的基本模型

CPU 寄存器里保存的是位模式。例如：

```text
0xfffffffffffffff0
```

同一组 64 位可以解释为：

```text
unsigned long: 18446744073709551600
signed long:   -16
```

寄存器本身并没有“有符号寄存器”和“无符号寄存器”的区别。

因此，分析整数运算时要分开看两件事：

1. 指令对位模式做了什么；
2. 程序准备怎样解释结果。

对于普通的 `add`、`sub`、`and`、`or`、`xor`，有符号和无符号数据通常使用相同指令。真正的差别主要体现在：

- 条件判断选择哪一组条件码；
- 右移使用 `shr` 还是 `sar`；
- 乘法是否需要完整高半部分；
- 除法使用 `div` 还是 `idiv`；
- 扩展操作使用零扩展还是符号扩展。

---

# 2. `add`、`sub` 与固定宽度整数

最基本的加法：

```asm
addq %rsi, %rax
```

可以理解为：

```text
RAX = RAX + RSI
```

减法：

```asm
subq %rsi, %rax
```

表示：

```text
RAX = RAX - RSI
```

`q` 表示 64 位操作。同样还有：

```text
addb / subb    8 位
addw / subw   16 位
addl / subl   32 位
addq / subq   64 位
```

CPU 只保留目标宽度能够容纳的低位结果。

例如 8 位加法：

```text
250 + 10 = 260
```

260 的十六进制是：

```text
0x104
```

但 8 位寄存器只能保存低 8 位：

```text
0x04
```

因此，固定宽度整数运算本质上是在模 `2^N` 的范围中进行。

### 标志位

`add` 和 `sub` 会更新上一课学习过的主要标志位：

```text
ZF  结果是否为 0
SF  结果最高位是否为 1
CF  无符号进位或借位
OF  有符号溢出
```

同一条 `add` 指令可以同时产生 `CF` 和 `OF`，后续代码根据数据类型选择需要的解释。

---

# 3. `neg`、`inc` 与 `dec`

## 3.1 `neg`

```asm
negq %rax
```

可以理解为：

```text
RAX = 0 - RAX
```

在二进制补码中，这等价于：

```text
按位取反
再加 1
```

例如：

```text
RAX = 5
negq %rax
RAX = -5
```

`neg` 会修改算术标志位。

其中有两个边界值得注意：

- 操作数为 0 时，没有发生借位，因此 `CF=0`；
- 非 0 操作数执行 `neg` 时 `CF=1`；
- 最小有符号整数取负仍无法在相同宽度中表示，因此会产生有符号溢出。

对于 64 位整数：

```text
0x8000000000000000
```

按有符号解释是 `LONG_MIN`。它的数学相反数超出了 64 位 signed long 的正数范围。

## 3.2 `inc` 和 `dec`

```asm
incq %rax
decq %rax
```

分别完成加 1 和减 1。

它们与：

```asm
addq $1, %rax
subq $1, %rax
```

有一个重要区别：

> `inc` 和 `dec` 不修改 `CF`。

因此，在需要保留进位状态的代码中，这个差别很重要。

阅读反汇编时不要简单把 `inc` 当成完全等价的 `add $1`。

---

# 4. 位运算：`and`、`or`、`xor`、`not`

位运算直接对每一位进行处理。

假设：

```text
A = 11001010
B = 10101100
```

那么：

```text
A AND B = 10001000
A OR  B = 11101110
A XOR B = 01100110
NOT A    = 00110101
```

## 4.1 `and`：保留指定的位

```asm
andq $0xff, %rax
```

只保留 `RAX` 的低 8 位。

这类操作常用于掩码：

```c
value &= mask;
```

## 4.2 `or`：设置指定的位

```asm
orq $0x4, %rax
```

会把 bit 2 设置为 1，其他位保持原值。

对应：

```c
value |= 0x4;
```

## 4.3 `xor`：翻转指定的位

```asm
xorq $0x4, %rax
```

会翻转 bit 2。

特别常见的是：

```asm
xorl %eax, %eax
```

它把 `EAX` 清零。根据 x86-64 的 32 位写入规则，最终整个 `RAX` 都变成 0。

编译器经常用这种形式清零寄存器。

## 4.4 `not`：全部按位取反

```asm
notq %rax
```

每一位都翻转：

```text
0 -> 1
1 -> 0
```

与 `neg` 不同，`not` 只是按位取反，不执行加 1。

还有一个容易忽略的区别：

> `not` 不修改 `RFLAGS`。

而 `and`、`or`、`xor` 会更新条件标志；其中 `CF` 和 `OF` 被清零。

---

# 5. 左移：`shl` / `sal`

左移一位：

```asm
shlq $1, %rax
```

表示所有位向左移动一位，低位补 0，最高位被移出。

例如：

```text
00000101 = 5
左移 1 位
00001010 = 10
```

在没有发生有效位丢失时，左移 `n` 位相当于乘以：

```text
2^n
```

因此：

```asm
shlq $3, %rax
```

通常可以理解为：

```text
RAX *= 8
```

`sal`（shift arithmetic left）和 `shl`（shift logical left）在 x86 中是同一操作。

左移时低位总是补 0，因此不需要像右移那样区分逻辑左移和算术左移。

---

# 6. `shr` 与 `sar`：无符号右移和有符号右移

右移是本课最需要区分 signed/unsigned 的地方之一。

假设 8 位数据：

```text
11110000
```

它可以解释为：

```text
unsigned: 240
signed:   -16
```

## 6.1 `shr`：逻辑右移

```asm
shrq $2, %rax
```

高位补 0：

```text
11110000
  ↓ shr 2
00111100
```

这是无符号整数右移所需要的语义。

## 6.2 `sar`：算术右移

```asm
sarq $2, %rax
```

高位复制原来的符号位：

```text
11110000
  ↓ sar 2
11111100
```

8 位补码中：

```text
11110000 = -16
11111100 = -4
```

因此，C 中：

```c
int64_t a;
uint64_t b;

a >> 2;
b >> 2;
```

在常见 x86-64 编译结果中分别对应：

```asm
sarq $2, ...
shrq $2, ...
```

这也是从反汇编恢复变量类型的重要线索。

---

# 7. 移位次数为什么经常使用 `CL`

移位次数可以直接写成立即数：

```asm
shrq $4, %rax
```

如果次数运行时才知道，传统 x86 移位指令使用 `CL`：

```asm
movb $4, %cl
shrq %cl, %rax
```

64 位操作只使用移位计数的低 6 位，因此有效计数按 64 取模；32 位操作只使用低 5 位。

例如对 64 位值：

```text
count = 65
```

硬件实际使用的计数是：

```text
65 & 0x3f = 1
```

这一规则属于指令本身的语义。编写 C 代码时仍要遵守 C 语言对移位范围的规定，不能因为硬件会屏蔽计数就依赖越界移位。

### 移位与标志位

移位会把最后一个被移出的位写入 `CF`。

`OF` 的含义只在移位次数为 1 时有明确规定。对于更大的移位次数，不应依赖 `OF`。

---

# 8. 乘法为什么比加法复杂

两个 N 位整数相乘，完整结果最多需要 2N 位。

例如：

```text
64 位 × 64 位
```

完整结果可能需要 128 位。

因此必须先问：

> 程序只需要低 64 位，还是需要完整 128 位结果？

这决定了应该怎样理解 `imul` 和 `mul`。

---

# 9. `imul` 的常见形式

`imul` 是有符号乘法指令，但它有多种操作数形式。

## 9.1 两操作数形式

```asm
imulq %rsi, %rax
```

可以理解为：

```text
RAX = RAX * RSI
```

只保留低 64 位。

这是编译器实现普通 C 整数乘法时常见的形式。

## 9.2 三操作数形式

```asm
imulq $10, %rdi, %rax
```

表示：

```text
RAX = RDI * 10
```

同样只保留目标宽度的低位结果。

## 9.3 单操作数形式

```asm
imulq %rsi
```

这是另一种语义：

```text
RDX:RAX = RAX * RSI
```

它产生完整的 128 位有符号结果。

这里：

```text
RDX = 高 64 位
RAX = 低 64 位
```

因此看到单操作数 `imul` 时，要立刻注意 `RAX` 和 `RDX` 都是隐式寄存器。

---

# 10. `mul`：无符号完整乘法

无符号单操作数乘法：

```asm
mulq %rcx
```

表示：

```text
RDX:RAX = RAX * RCX
```

也是 64 位乘 64 位得到 128 位结果。

区别在于：

```text
mul   按无符号整数解释操作数
imul  按有符号整数解释操作数
```

如果程序只保留低 64 位，那么有符号和无符号乘法的低位位模式是一致的。这也是编译器经常只使用两操作数 `imul` 完成普通整数乘法的原因之一。

只有在需要判断高半部分、溢出或完整宽度结果时，signed/unsigned 的差异才更加明显。

---

# 11. 除法的核心：被除数是 `RDX:RAX`

x86-64 的传统整数除法使用固定的隐式寄存器。

64 位除法：

```text
被除数：RDX:RAX，共 128 位
除数：  指令显式操作数，共 64 位
商：    RAX
余数：  RDX
```

因此：

```asm
idivq %rcx
```

不能简单理解为：

```text
RAX /= RCX
```

准确模型是：

```text
RAX = (RDX:RAX) / RCX 的商
RDX = (RDX:RAX) / RCX 的余数
```

这解释了为什么除法之前必须正确准备 `RDX`。

---

# 12. 有符号除法：`cqto` + `idiv`

假设要计算：

```c
long q = -100 / 9;
```

首先：

```asm
movq $-100, %rax
```

但 `idivq` 使用的是 128 位被除数 `RDX:RAX`。

因此需要把 `RAX` 的符号扩展到 `RDX`：

```asm
cqto
```

`cqto` 的作用可以理解为：

```text
RDX:RAX = sign_extend(RAX)
```

如果 `RAX` 是负数：

```text
RDX = 0xffffffffffffffff
```

如果 `RAX` 是非负数：

```text
RDX = 0
```

然后：

```asm
movq $9, %rcx
idivq %rcx
```

结果：

```text
RAX = -11
RDX = -1
```

因为整数除法向 0 截断：

```text
-100 = (-11) * 9 + (-1)
```

余数与被除数具有相同符号。

### 相关指令

不同宽度有对应的符号扩展指令，例如：

```text
cltd / cdq   EAX -> EDX:EAX
cqto / cqo   RAX -> RDX:RAX
```

AT&T 和 Intel 工具可能显示不同助记符形式，但语义相同。

---

# 13. 无符号除法：准备 `RDX` + `div`

如果计算：

```c
unsigned long q = 100 / 9;
```

通常希望被除数只是普通的 64 位 `100`，而不是任意的 128 位数。

因此先把高 64 位清零：

```asm
movq $100, %rax
xorq %rdx, %rdx
movq $9, %rcx
divq %rcx
```

得到：

```text
RAX = 11
RDX = 1
```

这里：

```text
100 = 11 * 9 + 1
```

### 一个常见错误

下面的代码是不完整的：

```asm
movq $100, %rax
divq %rcx
```

因为 `RDX` 仍然是被除数的高半部分。

如果 `RDX` 中残留旧值，那么真正被除的是：

```text
RDX:RAX
```

而不是单独的 `RAX`。

---

# 14. 除法为什么会产生 `#DE`

整数除法有两个重要异常条件。

## 14.1 除数为 0

```asm
idivq %rcx
```

如果：

```text
RCX = 0
```

CPU 产生 Divide Error，即 `#DE` 异常。

## 14.2 商无法放入目标寄存器

即使除数不为 0，如果数学结果无法放入目标宽度的 `RAX`，也会产生 `#DE`。

因此 `div/idiv` 不只是普通算术操作，它们还可能改变控制流进入异常处理路径。

后面的异常课程会再分析 `#DE` 如何进入 Linux 内核异常入口。

# 15. 为什么编译器不一定使用 `imul` 完成常数乘法

假设：

```c
unsigned long scale_by_10(unsigned long x)
{
    return x * 10;
}
```

编译器可能生成：

```asm
leaq (%rdi,%rdi,4), %rax
addq %rax, %rax
```

第一条得到：

```text
x + 4*x = 5*x
```

第二条再乘 2：

```text
10*x
```

这说明：

> 高级语言中的乘法不保证对应一条 `imul`。

编译器会根据目标 CPU、优化级别和常数选择等价实现。

反汇编分析应从语义出发，而不是机械寻找某个指令名称。

---

# 16. 常数除法为什么可能没有 `idiv`

除法通常比加法、移位和乘法更复杂。

如果除数在编译时已经确定，例如：

```c
long divide_by_10(long x)
{
    return x / 10;
}
```

优化编译器常常把它转换成：

```text
乘以一个预先计算好的常数
+ 取乘积的高位
+ 若干移位和修正
```

因此在 `-O2` 反汇编中可能完全看不到 `idiv`。

这种常数通常称为 magic multiplier。它不是近似计算，而是编译器根据固定宽度整数除法规则构造的精确变换。

本课不要求推导 magic number 的生成算法，只需要建立一个重要认识：

> “C 中有除法”不等于“机器码中一定有 `div/idiv`”。

# 17. C 类型如何影响生成的指令

下面两个函数只有类型不同：

```c
int64_t signed_shift(int64_t x, unsigned int n)
{
    return x >> n;
}

uint64_t unsigned_shift(uint64_t x, unsigned int n)
{
    return x >> n;
}
```

典型 x86-64 输出分别是：

```asm
sarq %cl, %rax
```

和：

```asm
shrq %cl, %rax
```

同样：

```c
int64_t divide_signed(int64_t a, int64_t b)
```

通常形成：

```asm
movq %rdi, %rax
cqto
idivq %rsi
```

而：

```c
uint64_t divide_unsigned(uint64_t a, uint64_t b)
```

通常形成：

```asm
movq %rdi, %rax
xorl %edx, %edx
divq %rsi
```

因此，在没有源码的情况下，`sar`/`shr`、`idiv`/`div` 都可以帮助推断原始数据类型。

# 18. 与 Linux 内核代码的关系

本课的指令在内核中非常常见，但通常不会以“专门写一段汇编算术代码”的形式出现。

更常见的是编译器把 C 代码转换成这些指令。

例如内核中大量存在：

```text
状态位和掩码      -> and / or / xor / test
页大小和对齐      -> shift / and
索引和倍数计算    -> lea / shift / imul
计数器和长度      -> add / sub
固定常数换算      -> shift / multiply / magic division
```

阅读内核反汇编时，可以按下面的顺序恢复语义：

1. 确定操作宽度；
2. 判断数据按 signed 还是 unsigned 使用；
3. 判断结果是否只保留低位；
4. 检查是否使用 `RAX/RDX/RCX` 等隐式寄存器；
5. 再结合前后地址计算和条件跳转恢复 C 语义。

后面学习页表、时间计算和调度统计时，会再次遇到这些模式。

# 19. 常见误区

## 19.1 把寄存器分成“有符号寄存器”和“无符号寄存器”

寄存器只保存位模式。signed/unsigned 主要由指令语义和后续解释决定。

## 19.2 认为 `shr` 和 `sar` 都只是除以 2

对于非负数，两者可能得到相同结果；对于最高位为 1 的值，结果完全不同。

## 19.3 看到 `imul` 就认为一定需要完整 128 位结果

两操作数和三操作数 `imul` 通常只保留目标宽度的低位；单操作数形式才隐式产生 `RDX:RAX` 完整结果。

## 19.4 忘记 `div/idiv` 使用 `RDX:RAX`

这是分析除法错误最常见的原因之一。除法前必须检查 `RDX` 是如何准备的。

## 19.5 认为 C 的常数乘除法一定对应 `imul/idiv`

优化器可能使用 `lea`、移位、加法和 magic multiplier。

## 19.6 在多位移位后依赖 `OF`

`OF` 对移位次数大于 1 的情况不应作为程序判断依据。
