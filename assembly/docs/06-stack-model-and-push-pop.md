# 第 6 课（一）：栈的基本模型与 `push/pop`

前面的课程主要讨论寄存器、普通内存访问和控制流。本节开始引入栈。

这里先只解决架构层面的几个问题：

```text
栈到底是什么？
RSP 表示什么？
push 和 pop 对 RSP、内存和寄存器做了什么？
为什么说 x86-64 的栈向低地址增长？
手工 sub/add RSP 与 push/pop 有什么相同和不同？
```

`_start` 时的 `argc`、`argv`、`envp`、auxiliary vector，以及 System V AMD64 ABI 的栈对齐规则放在本课后续部分。这样可以先把 CPU 指令语义与 ABI 约定分开理解。

---

## 1. 栈首先是一段普通内存

从 CPU 的普通 load/store 视角看，栈并不是一种完全不同的存储介质。栈中的数据最终仍然位于内存中。

例如：

```asm
movq (%rsp), %rax
```

本质仍然是：

```text
以 RSP 中的值作为地址
→ 从该地址读取 8 字节
→ 写入 RAX
```

栈之所以具有“栈”的含义，是因为程序和指令把 `RSP` 当作当前栈顶指针，并按照约定移动它。

在 x86-64 中，许多指令会隐式使用 `RSP`，例如：

```text
push
pop
call
ret
```

本节只讨论前两个。`call/ret` 在 A07 中完整展开。

---

## 2. `RSP` 是当前栈顶地址

设某一时刻：

```text
RSP = 0x00007fffffffe000
```

把一个 64 位值压栈后，新的栈顶位于更小的地址：

```text
0x00007fffffffdff8
```

相差 8 字节。

因此常说：

> x86-64 栈向低地址增长。

这里的“增长”指的是：随着更多栈内容被压入，`RSP` 的数值变小，占用范围向低地址扩展。

示意：

```text
高地址

0x...e008
0x...e000   <- 原 RSP
0x...dff8   <- push 一个 8 字节值后的 RSP
0x...dff0   <- 再 push 一个 8 字节值后的 RSP

低地址
```

不要把“向低地址增长”理解成所有内存写入都必须从高向低进行。它描述的是栈顶指针在典型栈操作中的移动方向。

---

## 3. `pushq` 的精确效果

考虑：

```asm
movabsq $0x1122334455667788, %rax
pushq %rax
```

对 64 位 `push`，可以用下面的逻辑模型理解：

```text
RSP = RSP - 8
memory[RSP ... RSP+7] = RAX
```

也就是：

1. 先为新元素腾出 8 字节；
2. 再把值写到新的栈顶。

假设执行前：

```text
RSP = 0x1000
RAX = 0x1122334455667788
```

执行后：

```text
RSP = 0x0ff8
*(uint64_t *)0x0ff8 = 0x1122334455667788
```

注意，x86 是 little-endian，因此从低地址逐字节观察内存会看到：

```text
88 77 66 55 44 33 22 11
```

但把这 8 字节作为一个 64 位整数读回时，数值仍然是：

```text
0x1122334455667788
```

---

## 4. 连续两次 `push` 为什么形成 LIFO

假设：

```asm
pushq %rax    # A
pushq %rcx    # B
```

第一次执行后：

```text
RSP = S - 8
[RSP] = A
```

第二次执行后：

```text
RSP = S - 16
[RSP]     = B
[RSP + 8] = A
```

内存布局变成：

```text
高地址

S          原栈顶
S - 8      A
S - 16     B   <- 当前 RSP

低地址
```

因此当前栈顶总是最后压入的 B。

这就是 LIFO：

```text
Last In, First Out
后进先出
```

LIFO 并不是由一种特殊“栈内存”自动提供的，而是由 `RSP` 的移动方式和 `push/pop` 的语义共同形成的。

---

## 5. `popq` 的精确效果

考虑：

```asm
popq %r9
```

可以用下面的逻辑模型理解：

```text
R9 = memory[RSP ... RSP+7]
RSP = RSP + 8
```

即：

1. 读取当前栈顶的 8 字节；
2. 写入目标寄存器；
3. 栈顶向高地址移动 8 字节。

延续上一节的状态：

```text
[RSP]     = B
[RSP + 8] = A
```

第一次：

```asm
popq %r9
```

得到：

```text
R9  = B
RSP = S - 8
```

第二次：

```asm
popq %r10
```

得到：

```text
R10 = A
RSP = S
```

因此取出顺序与压入顺序相反。

---

## 6. `pop` 不会“擦除”原来的内存

这是理解栈时很重要的一点。

执行：

```asm
popq %rax
```

主要发生的是：

```text
读取 [RSP]
RSP += 8
```

CPU 并不会为了完成 `pop`，再额外把刚才的内存位置清零。

因此从物理的内存内容看，旧字节通常仍然留在那里，直到后续代码重新使用或覆盖这块内存。

所以“一个值已经出栈”的真正含义是：

> 它已经不再属于当前由 `RSP` 定义的有效栈顶范围。

而不是：

> 那几个字节已经被硬件擦除。

这个区别以后理解未初始化栈数据、栈信息泄漏和 crash dump 时都很重要。

---

## 7. `push/pop` 对 `RFLAGS` 的影响

普通 `push` 和 `pop` 不根据被压入/弹出的普通数据更新算术条件标志。

也就是说，它们不像：

```asm
addq
subq
cmpq
```

那样重新计算：

```text
ZF
CF
SF
OF
```

因此可以有：

```asm
cmpq %rsi, %rdi
pushq %rax
popq %rax
je equal
```

如果中间没有其他会修改相关标志的指令，`je` 仍然可以读取前面 `cmpq` 产生的 `ZF`。

这也是分析汇编时需要区分的一点：

```text
某条指令改变了 RSP
```

并不意味着：

```text
它一定改变了算术标志位
```

---

## 8. 手工调整 `RSP`

程序并不一定只能靠 `push` 扩展栈。

例如：

```asm
subq $16, %rsp
```

会把 `RSP` 向低地址移动 16 字节，相当于人为保留一块栈空间：

```text
原 RSP = S
新 RSP = S - 16
```

然后可以普通寻址：

```asm
movq %rax, 8(%rsp)
```

最后：

```asm
addq $16, %rsp
```

把栈顶恢复。

这类模式以后会频繁出现在函数栈帧中：

```text
sub $N, %rsp
    使用局部栈空间
add $N, %rsp
```

---

## 9. `sub/add RSP` 与 `push/pop` 不能简单视为完全相同

从“移动栈顶”的角度，它们有相似之处。

例如：

```asm
pushq %rax
```

与下面两步在很多普通场景中有相似的最终数据效果：

```asm
subq $8, %rsp
movq %rax, (%rsp)
```

但不能因此说两者完全等价。

最直接的差异之一是：

```asm
subq $8, %rsp
```

会按照算术减法规则更新 `RFLAGS` 中的条件标志，而普通：

```asm
pushq %rax
```

不会因为调整 `RSP` 而产生这样的算术标志更新。

同理：

```asm
addq $8, %rsp
```

会更新算术标志，而普通 `popq` 不会。

因此，如果前面的代码刚刚通过 `cmp/test` 产生了后续还要使用的条件标志，手工 `sub/add` 可能覆盖这些标志，而 `push/pop` 本身不会。

后续课程分析编译器生成的函数序言和尾声时，需要同时观察：

```text
RSP 是否变化
内存是否变化
RFLAGS 是否变化
```

---

## 10. `RSP` 必须始终指向可访问的栈区域

虽然：

```asm
subq $4096, %rsp
```

从整数运算角度只是修改一个寄存器，但程序随后若访问：

```asm
movq %rax, (%rsp)
```

这个地址必须是当前进程可以访问、具有相应权限的虚拟地址，否则会触发异常。

因此需要区分：

```text
CPU 指令语义
```

与：

```text
操作系统为进程建立并管理的用户栈虚拟内存
```

本节研究前者。用户栈的虚拟内存布局、增长限制和缺页处理属于内存管理领域，在 [`../../memory/`](../../memory/) 中完整展开。

---

## 11. 不要把当前用户栈与内核栈混为一谈

本节实验在用户态 ELF 程序中运行，因此当前 `RSP` 指向的是用户地址空间中的栈。

以后执行系统调用、异常或中断进入内核时，内核会使用内核态执行所需的栈结构。那一部分与系统调用入口、异常入口和任务上下文有关，会在后面的 A14～A17 中结合 Linux 5.10 源码分析。

此处只需要先建立一个稳定模型：

```text
RSP 指向当前正在使用的栈顶
push/pop 隐式修改 RSP
栈中的内容最终仍是内存中的字节
```

## 12. 实验：逐步观察 `RSP` 和内存

配套实验：

[`../labs/06-stack-push-pop/`](../labs/06-stack-push-pop/)

实验会保存初始 `RSP`，然后执行两次 `pushq`、两次 `popq`，验证：

```text
第一次 push: RSP = initial - 8
第二次 push: RSP = initial - 16
第一次 pop : 得到后压入的值
第二次 pop : 得到先压入的值
最终 RSP   : 恢复到 initial
```

同时再使用：

```asm
subq $16, %rsp
movq %rax, 8(%rsp)
addq $16, %rsp
```

验证“分配栈空间”和“压入一个值”是两个相关但不完全相同的概念。

## 13. 本节应形成的判断方法

看到栈相关汇编时，逐条问：

```text
执行前 RSP 是多少？
这条指令让 RSP 增加还是减少多少？
新的 [RSP] 指向什么？
哪些内存位置被读写？
数据是几字节？
旧栈内存是否仍然存在？
RFLAGS 是否被修改？
```

如果这些问题都能准确回答，后续理解 `call/ret`、函数栈帧、System V AMD64 ABI 和内核入口代码会容易很多。

## 14. 本节小结

本节只需要牢固掌握下面的主线：

```text
pushq value
    ↓
RSP -= 8
[RSP] = value

popq reg
    ↓
reg = [RSP]
RSP += 8
```

并记住四点：

1. 栈内容最终仍位于普通虚拟内存中；
2. x86-64 栈通过 `RSP` 向低地址扩展；
3. `pop` 移动栈顶，但不会自动擦除旧内存；
4. 手工 `sub/add %rsp` 可以管理栈空间，但其 `RFLAGS` 语义与 `push/pop` 不同。
